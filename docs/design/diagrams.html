ph-statement-import · call flow diagrams

How the Python modules call each other once the app runs on Google Cloud in hosted mode with Gmail auto-import, after the refactors in docs/plan/P1-refactors.md. The code has three parts: a Source (one per e-wallet or bank) turns statement rows into neutral Transactions, and YNAB (ynab_api/) formats and uploads them. The GCP architecture is in gcp-architecture.drawio and the screens are in wireframes.html.

D2 · Call flow between .py files

Arrows point from the caller to the module it calls. Everything is under statement_etl/. The web app is split into blueprints, one per job. Parsers never import YNAB code: they return Transactions, and ynab_api/format.py turns those into YNAB's format. convert.py (formerly transform.py) only picks the source and calls its converter; transaction.py only defines the Transaction shape.

U1 · Manual upload (web and command line)

The web page and the CLI call the same three pipeline functions. import_statement() is the one place that sets a new account's starting balance, uploads, and checks the ending balance. Every YNAB call from the web gets its token from the YNAB auth blueprint, which refreshes it when needed.

U2 · Gmail auto-import poll (all new)

Cloud Scheduler calls /tasks/poll-gmail every 15 minutes, and the OIDC token is checked before any work. For each user, the runner searches Gmail once per mapped wallet and imports new statements into that wallet's YNAB account, with the same parse_statement() and import_statement() as the manual upload. Users and wallets are handled separately, so one failure doesn't stop the rest. Tokens and password inputs are decrypted in the app (MultiFernet, with keys from the app-config secret); there's no Cloud KMS.

U3 · Adding a source (the Source contract)

What a contributor writes to support a new e-wallet or bank: one parser module plus one Source entry. The source returns neutral Transactions and never touches YNAB code. key is a stable id within the source: GCash uses its Reference No.; GoTyme has none, so it uses date|credits|debits|running balance|n. YNAB's import_id is make_import_id(source, key), so re-importing never creates duplicates.
